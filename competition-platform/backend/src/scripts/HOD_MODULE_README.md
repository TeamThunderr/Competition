# HOD Module Documentation 🎓

This document provides a comprehensive overview of the **Head of Department (HOD)** module within the Competition Platform. It covers the architecture, file structure, API endpoints, and feature details.

## 1. Module Overview

The HOD module is designed to give Department Heads oversight and control over their department's activities. It includes:
- **Dashboard**: High-level statistics of students, competitions, and submissions.
- **Analytics**: Detailed breakdowns of student distribution (Batch/Year) and performance (CGPA/Participation).
- **OD Management**: Workflow for approving or rejecting On-Duty requests from shortlisted students.
- **Competition Insights**: View of all competitions and department-specific participation metrics.

## 3. API Endpoints 🔌

All routes are prefixed with `/api/hod` and protected by **Auth** and **Role** guards.

### Dashboard & Analytics
- `GET /stats`: Basic department statistics (legacy).
- `GET /dashboard-analysis`: **(New)** Consolidated endpoint for Summary Cards, Batch Charts, and Academic Year tables.
- `GET /users`: Fetches list of all users (Students/Faculty) in the department.

### Competitions
- `GET /competitions`: List all competitions.
- `GET /competition/:id`: Get details of a specific competition.
- `GET /competition/:id/stats`: Get department-specific stats for a competition.

### OD Management
- `GET /pending-od`: Fetch all pending OD requests for the department.
- `POST /manage-od`: Approve or Reject a request.
  - **Body**: `{ "request_id": "UUID", "status": "APPROVED" | "REJECTED" }`

## 4. Key Features & Implementation Details 🛠️

### A. Dashboard Analysis
- **Data Source**: Aggregates data from `users`, `registrations`, `competition_status`, and `od_requests`.
- **Logic**:
  - **Batch Calculation**: Derived from `admission_year` (e.g., `2024` -> `2024-2028`).
  - **Academic Year**: Calculated dynamically based on `currentYear - admissionYear`.
  - **Performance**: Optimized SQL queries (using specific foreign key joins) to prevent N+1 issues.

### B. Access Control
- **Middleware**: `roleMiddleware.js` ensures strict access.
- **Data Isolation**: All queries use `req.user.department_id` to strictly filter data. An HOD cannot see data from other departments.

### C. OD Approval Workflow
1.  **Student** requests OD (only if Shortlisted).
2.  **HOD** sees request in `OdApprovals.jsx`.
3.  **Action**: HOD clicks "Approve".
4.  **Backend**: Updates `od_requests` status to `APPROVED` and logs the approver ID.

## 5. Security Note 🔒

- **Authentication**: JWT-based (Supabase Auth).
- **Authorization**: Server-side role validation.
- **Row Level Security**: Database policies supplement the API logic for an extra layer of defense.
